# Consolidated UI and usability audit

24 October 2026 · PETSCII Graphics Lab

## Scope and evidence

This consolidates the owner's recommendations and two additional analytical passes: visual interface design and task usability. It is an expert-style assessment, not an independent human review or an observed user study. Recommendations are proposals, not implemented changes or accessibility certification.

Evidence: current implementation, existing roadmap and UI review, and the portrait/landscape captures of the deployed build. Captures use Chromium emulation at iPad 7 viewport sizes, 810 × 1080 and 1080 × 810 CSS pixels at 2× resolution. They do not establish physical iPad Safari or VoiceOver behavior.

The Raskin-informed goal is to reduce mode errors, attention shifts and remembered instructions while preserving reliable habits. A familiar drawing-tool palette still has modes; familiarity alone does not remove their costs.

## Compact controls: size, readability and recognition

Prototype control labels at 13–14 CSS pixels, with readable explanations that can enlarge. Some existing notes are already approximately 11–12 pixels: do not shrink those automatically. Retain browser text scaling, sufficient contrast and visible keyboard focus.

Specify whether a percentage concerns area or dimensions. For an illustrative 44 × 44 square, 25% less area gives approximately 38 × 38; shrinking each dimension by 25% gives 33 × 33, about 44% less area. Prototype roughly 38–40-pixel compact targets first, comparing touch error rates with the existing 44-pixel baseline. These are design candidates, not established successful sizes.

Visible icon, button background and hit area are separate measurements. Extra invisible hit area is useful only where it does not overlap adjacent targets. Do not sacrifice spacing or hide labels solely to fit every command into one row. Avoid introducing a density preference unless testing demonstrates a real need; first try a compact default that respects accessibility settings.

WCAG 2.2 AA target-size minimum is 24 × 24 CSS pixels, subject to specified exceptions; this is not evidence that 24 pixels is comfortable on iPad. Keyboard access and alternatives to dragging require separate evaluation.

## Help: what to hide and what to retain

| Keep visible at the point of action | Put behind contextual question-mark help |
| --- | --- |
| Active tool, ink and selection state | Fill matching rules; selection/duplicate instructions |
| Crop consequences and Apply/Cancel | General resize explanation |
| Playing/paused/read-only state | Replay details; cycles versus duration; waveform descriptions |
| Output dimensions, duration and loop count | Format comparisons and detailed background/transparency behavior |
| Save failures, invalid values and export blockers | Autosave mechanics, glyph provenance and technical C64 reference |
| Relevant limits and remedy | Why hardware imposes those limits |

Use one help trigger per meaningful group or unfamiliar concept, rather than a question mark on every control. Eliminate redundant prose before relocating it. Example: Animation timing [?], with short explanations and a concrete timing example.

Implement tap-to-open help popovers with short headings, specific accessible names, keyboard activation, appropriate expanded/control relationships, Close and Escape, and appropriate focus restoration. Do not depend on hover, long press or HTML title text. Interactive help containing links or a Close button needs suitable disclosure/dialog semantics rather than pretending to be a noninteractive ARIA tooltip.

Keep help open while it is being read, within the viewport and legible at enlarged text. Dismissing help over the canvas must not accidentally paint underneath. Prefer opening on deliberate activation to avoid interruptions when merely moving focus through the palette.

## C64 exports: make feasibility understandable before download

The current implementation performs native export validation after the Download action. Failed attempts make the owner infer how dimensions, content, movement and color changes interact. Canvas size alone cannot express export feasibility.

| Capacity dimension | Required presentation |
| --- | --- |
| Geometry | Actual drawing dimensions against the native supported dimensions |
| Character patterns | Distinct patterns required across the entire sampled animation, including blank |
| Program memory | Generated program and stream size against the exporter budget |
| Update workload | Worst frame and loop-transition work against the selected timing budget |
| Validation confidence | Distinguish measured/generated facts, conservative estimates and machine-tested support |

Use states such as Ready, Needs adjustment, Checking and Unable to check. Do not imply that a single overall percentage or generic green indicator guarantees smooth hardware playback. Keep PRG and D64 capacity results consistent; disk packaging does not increase the player's animation budget.

Return all relevant blockers with remedies ranked by usefulness. A slower loop may help update time without fixing memory or pattern count. A smaller drawing may help workload without reducing the number of unique patterns enough. Recommend only changes that address the identified blocker.

Offer explicit, non-destructive adjustments after evaluating them: for example, a supported longer loop duration. Preview the change and require a deliberate Apply action; do not silently crop, discard glyphs, alter effects or reduce quality. Preserve an undoable route back to the original settings.

Preflight should share the exporter's validation logic and captured inputs. Debounce expensive checking during edits, discard stale results and cancel obsolete checks. Revalidate on download; a cached Ready result must not describe older artwork. Failure to run a check is different from an animation exceeding a limit.

The requested capacity benchmark is 40 × 24 movement waves plus color waves, with detailed patterns and widespread ink changes. Record memory, update time, timing variation, loop drift and achievable speed on PAL/NTSC. Compare encoding/decoder improvements, staged updates and native procedural effects, including the mixed-bank RAM glyph path. Declare any approximation explicitly. This investigation must retain RUN/STOP, restoration and bounded memory; it does not remove the separate character-pattern limit.

## Additional usability-pass findings

1. Reduce work, not merely visible text. An extra help tap for every task would replace visual clutter with interaction cost. Core tasks should work without consulting help.
2. Reserve stable space for contextual actions, or anchor them near their subject. Selection creation should not shift the canvas and invalidate the user's spatial expectation.
3. Treat Clear, Delete, Recolor and ordinary drawing as visibly distinct scopes. Prefer previews and dependable Undo over routine confirmation dialogs; use confirmation selectively where recovery is unavailable.
4. Keep optional technical knowledge optional. Users should not need glyph IDs, VIC memory addresses or compression terminology to export art.
5. Improve the first-use path. A concise invitation to choose a glyph and draw can replace a permanent Help section; retain a discoverable route back to instructions.
6. Identify outcomes with visible feedback near the action. Explain why a control is unavailable through reachable text/help; a disabled control's hover title is insufficient on touch.
7. Account for the hand and Pencil. Test reach, accidental taps and occlusion, not just screenshots and absence of overflow.
8. Avoid noisy screen-reader announcements. Announce completed actions and meaningful warnings; do not announce every pointer movement or continually regenerated capacity estimate.

## Implementation sequence

1. Stabilize layout and recovery controls; decide stamp removal; simplify the status region.
2. Prototype compact type/icons/targets and portrait settings behavior; compare against the captured baseline.
3. Clarify selection, cancellation, non-drag alternatives and Undo semantics.
4. Consolidate help and implement accessible contextual popovers.
5. Add C64 preflight feedback and evaluated remedies; pursue capacity improvements as a separate technical workstream.
6. Validate end-to-end tasks and record remaining limitations before deployment.

## Acceptance and evaluation

| Task / condition | Evidence required |
| --- | --- |
| Choose glyph/ink; draw, erase, undo and resume | Complete without settings scrolling or opening help; record errors and hesitation |
| Line/rectangle, cancel and undo | Preview is clear; cancellation and Undo preserve project/replay/export accuracy |
| Select, move, duplicate and delete | Correct region/colors, understandable scope, no unexpected canvas movement; touch and keyboard alternatives |
| Preview, pause, return to drawing | State and recovery are understandable without explanation |
| Save editable art and download a shared image | Users distinguish the two outcomes without assistance |
| Export an over-limit C64 animation | Identify the actual blocker and useful remedy before attempting download; detect stale preflight |
| 810 × 1080 and 1080 × 810, including enlarged text | No orphan recovery controls, clipped controls, inaccessible help or lost canvas access |
| Touch, Pencil, mouse, keyboard and VoiceOver | Record recognition, accidental activation, focus order/return and task completion |

Measure completion, wrong-tool actions, accidental taps, recovery steps and help openings against the baseline. Do not claim improvements from smaller screenshots alone. Use browser regression checks for deterministic behavior; physical iPad and observed user sessions establish reach and practical usability.
